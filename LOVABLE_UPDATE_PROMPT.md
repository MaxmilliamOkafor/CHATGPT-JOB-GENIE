Update my existing Job Genie Lovable app to align with the extension changes in draft PR #1 of MaxmilliamOkafor/CHATGPT-JOB-GENIE. Inspect the existing app and schema first; preserve working authentication and existing user data. Implement the changes, test them, and report remaining limitations.

Replace hardcoded profile-match percentages with keyword coverage computed from the actual final CV: matched unique terms / total unique terms. 8 of 19 must show 42%; no keywords must show an unmeasured state. 3. Improve relevant coverage by mapping job requirements to explicit evidence in the saved profile. Suggest truthful synonyms and clearer descriptions. Show the supporting source for each proposed addition, and ask the candidate to confirm new facts. Never invent employment, dates, metrics, education, citizenship, authorization or skills. Separate missing evidence, keyword wording gaps and eligibility questions.
4. Add a screening-answer editor that stores exact question text, answer, applicable country/employer, and confirmation timestamp. Integrate through the extension's existing profile sync contract: ua_profile or ats_profile application_answers is a question-to-answer map. Inspect existing sync code before changing its schema. Leave unknown screening answers unresolved. Do not infer U.S. work authorization from Irish residence or EU citizenship. Explain which required questions need review.

Resolve accessible labels and associated listboxes, wait for options, select exact unambiguous values, and verify committed selection. Keep user answers intact. 6. Generate CV and cover-letter previews, downloads and attachments from the same reviewed text and job identity. Invalidate stale artifacts when text or job changes, and clear failed exports. Preserve phone digits, Unicode, technical skills, dates and names. Deduplicate repeated location components. Use a single-column document with conventional sections, selectable text, readable font sizes and no clipped content. Do not silently remove experience to force a page limit. Validate DOCX ZIP/XML and PDF text, render every page, and compare extracted text with the preview. Include cover-letter grammar checks and supported job-specific evidence.
7. Show recruiter-contact provenance and confidence. Filter accommodation, privacy, support and unrelated inboxes. Require recipient review. Keep provider secrets server-side, use per-user authorization, bound enrichment cost, and show actionable errors when credentials or credits are absent.

Provide a concise implementation report, migration requirements, screenshots, test results, and remaining deployment gates. Do not deploy or merge without a separate instruction.

Preserve the original CV template and compact single-screen extension layout. Use blue selection colors. Both employer attachments must be DOCX; never fall back to a stale PDF. Website changes alone cannot update the installed extension.

Excluded keywords: add a jsonb column excluded_keywords to public.profiles, NOT NULL DEFAULT '[]'::jsonb, covered by the existing owner-scoped RLS on that table so a user reads and writes only their own row. Each element is { id, term, covers, note, at }: id is the canonical requirement key, term is what the user typed or clicked, covers is the synonym group the exclusion reaches, at is ISO 8601. The extension reads this column on open and PATCHes it on every add and remove, so it must be selectable through the existing profiles select and updatable through the existing profiles update. Surface the list in the profile or settings area: show each excluded term with the synonyms it covers, let the user add one by typing and remove one in a click, and say plainly that an excluded term is never tailored into a CV or cover letter on any device. Do not deduplicate or rewrite the stored terms server-side, do not reorder them, and do not drop entries whose id is unfamiliar. Apply the same exclusions anywhere the site itself computes keyword coverage or proposes CV additions, so the site and the extension never disagree about which requirements are in play.

Professional summary shape (tailor-application, RULE 7): the summary must read as a description of the person and be checkable. Two sentences, 150 to 220 characters: "Background in <the candidate's actual field, in that field's own words>, with strengths in <two capabilities the EXPERIENCE section evidences>. <strongest outcome with its figure>; <second outcome with its figure>." Do not open with a held job title. On an application to another field a held title announces the wrong profession in the first line a screener reads, and on a pivot it is the least relevant true thing on the page; naming the field and the strengths says what transfers without claiming a job never held. Never put in the summary: a title the candidate has not held, the posting's own title, employer names, total years of experience, place names, any adjective describing the candidate, any self-rating, first person, "seeking" or "looking for", or any tool, technology or comma-separated skill run. Do not write a closing sentence naming the target role: the extension's recruiter audit appends one, and two of them read as a draft nobody finished. Strength terms must be in the posting's wording and evidenced by an experience bullet, never by the skills list alone; if fewer than two qualify, omit the strengths clause rather than pad it. Two outcomes joined by a semicolon, figures exactly as the profile states them, never rounded, dropped or invented. Rank outcomes by a before-and-after, then a magnitude, then a percentage, then a count, and choose the outcomes the posting cares about over the biggest numbers on the CV: a coaching posting is better served by "trained 24 analysts across two offices" than by a batch job going from six hours to one.

Evidence reading (_shared/evidence.ts): buildEvidenceSources must read every shape a profile arrives in, not one. Accept professionalExperience and professional_experience, relevantProjects and relevant_projects, and on each record read bullets, description, achievements and responsibilities for demonstrations and technologies, techStack, tech_stack and skills for records. Unwrap nested values rather than stringifying them: an achievement stored as { text } must yield its text, not "[object Object]". Drop a source already held, because the same role reached through two aliases is one piece of evidence and duplicating it reads as corroboration. A reader that knows only camelCase returns nothing at all against a stored snake_case profile, every requirement then classifies as unsupported, and the tailoring has no evidence to write from.

Bias and truthfulness in generated documents: never write a language proficiency as "native", "native speaker", "mother tongue" or "first language" - use "fluent", because native fluency names where someone is from and what an employer needs is whether they can work in the language. Keep a right-to-work statement such as "EU Citizen": it is a legal status that costs an employer money to get wrong and names no nationality. Never state total years of experience in a summary. Never present years in one field as meeting a stated requirement for years in another: a posting asking for "1+ years of front-of-house hospitality operations at a hotel" is not met by eight years of software engineering, and a sentence claiming otherwise is a false statement on an application. Equipment is not a capability: internet, wifi, laptop, webcam, headset, workspace and transportation are conditions a job needs present in a room, never skills, and must never appear in a skills section.

Excluded keywords, second pass: the extension now fills in the synonym group for a term the site stored with only the spelling that was typed, and writes it back. Expect the covers array on an existing entry to grow between reads. Do not treat that as corruption, do not rewrite or reorder it, and keep matching on term plus every entry in covers so the site and the extension agree about which requirements are in play. Keep preserving entries whose id is unfamiliar: the extension derives identity from the term on every read and never trusts a stored id, so an id written by either side is advisory only.

New edge function, extract-skills-evidence: deploy it and set OPENAI_API_KEY as a function secret. It sends a job description to the model under a fixed extraction specification held in prompt.ts and returns the reply unchanged; it must decide nothing, because validation runs in the extension against the posting that side holds. Keep the posting as a separate JSON user message and never concatenate it into the instructions. On failure return the status only, never the upstream body or the request headers, since both can carry the credential. With the secret unset return 503 with a reason naming the missing credential, never an empty skills list, because an empty list reads as a posting with no skills in it. Do not add a score, a match percentage or an ATS verdict to its output.
