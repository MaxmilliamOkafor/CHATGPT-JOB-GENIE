# Evidence-backed skill extraction

An independent implementation inspired by publicly described behaviour. It is
not Jobscan's algorithm, does not reproduce its score, does not model any
particular applicant tracking system, and does not extract skills perfectly.

## Why this is separate from the taxonomy

The rest of Job Genie answers **"does the CV cover this requirement?"** and
answers it generously through `keyword-taxonomy.js`: a CV saying Postgres
covers a posting saying PostgreSQL, ML satisfies Machine Learning, a plural
satisfies its singular. That is correct for deciding coverage.

This answers **"what does the posting actually say, and can each answer be
quoted back to it?"** Generosity is a defect there, so `skill-evidence.js`
shares nothing with the taxonomy and imports nothing. SQL inside MySQL is not
SQL. C inside C++ is not C. `managed teams` does not contain `management`.

Extraction rules and matching rules are separate on purpose:

| | where | what decides |
|---|---|---|
| Extraction | `website/supabase/functions/extract-skills-evidence/` | the model, under `prompt.ts` |
| Validation and matching | `skill-evidence.js` | code, with no model involved |

## Files

- `skill-evidence.js` — validation, deduplication, literal matching, report
  assembly, and the JSON schema. No network, no dependencies, runs in the
  popup and under Node.
- `website/supabase/functions/extract-skills-evidence/prompt.ts` — the
  extraction specification verbatim, plus the schema the reply is constrained
  to. Held as its own file so a change to it is a visible change.
- `website/supabase/functions/extract-skills-evidence/index.ts` — the model
  call. Reads `OPENAI_API_KEY` from the environment and returns the reply
  unchanged; it decides nothing.
- `tests/a-skill-needs-a-quotation.test.cjs` — 76 offline checks, including
  all nine from the supplied reference implementation.

## Setup for live extraction

The key is a function secret. It is never in the extension, never in
`manifest.json`, and never committed.

```bash
supabase secrets set OPENAI_API_KEY='<your key>'
supabase secrets set OPENAI_MODEL='<a Responses API model supporting Structured Outputs>'
supabase functions deploy extract-skills-evidence
```

`OPENAI_MODEL` is optional; without it the function uses
`gpt-4o-2024-08-06`. A caller may pass `model` to override per request.

With the secret unset the function returns `503 no_credentials` and says so,
rather than reporting the posting as having no skills in it.

## Use

```js
const report = await tailor.extractSkillsWithEvidence(jobDescription, cvText);
```

The CV argument is optional and is **never sent anywhere**. The comparison is
a string search that runs in the popup.

## What the report contains

`hard_skills` and `soft_skills` as separate lists, each record carrying its
exact source quotation, requirement status (`required` / `preferred` /
`unspecified`), review flags with reasons, and zero-based source offsets with
exclusive ends. Plus `rejected_records`, each with the reason it failed, and
`needs_review`.

Degrees, certifications, job titles, years of experience and eligibility are
outside the skill lists by specification.

## Illustrative example

**Not generated by a live model call.** The extraction half of this has not
been run against the API in this environment; the record below is written by
hand to show the shape, and the validation and matching half that processes it
is exercised by the test suite.

Job description:

```
Requirements: Strong SQL and Python. Excellent communication skills.
Nice to have: experience with MySQL.
```

Report (abridged):

```json
{
  "method": "proposed_extractor_v1_not_jobscan",
  "matching": "case-insensitive literal phrases; flexible whitespace; no stemming or synonyms",
  "hard_skills": [
    { "term": "SQL", "category": "hard_skill", "requirement": "required",
      "evidence": "Requirements: Strong SQL and Python.",
      "jd_literal_count": 1, "review_required": false, "review_reason": "" }
  ],
  "soft_skills": [
    { "term": "communication skills", "category": "soft_skill", "requirement": "required",
      "evidence": "Excellent communication skills.",
      "jd_literal_count": 1, "review_required": false, "review_reason": "" }
  ],
  "rejected_records": [],
  "needs_review": false
}
```

Note that `SQL` has `jd_literal_count: 1`, not 2. The posting contains the
letters S, Q, L a second time inside `MySQL`, and that is not a mention of
SQL. `Excellent` is dropped from the soft skill because the remaining
substring still names the complete skill.

## What has been tested, and what has not

**Tested**, offline, 76 checks: token boundaries across `SQL`/`MySQL`,
`C`/`C++`/`C#`, `Java`/`JavaScript`, `R`; source offsets and whitespace
flexibility across line breaks; no stemming and no synonym resolution;
fabricated quotations rejected; substring-only terms rejected; every malformed
record shape rejected by name; conflicting duplicates merged and flagged;
genuine wording variants preserved; source ordering; requirement status
carried unchanged; empty extraction producing an empty report rather than an
error; refusals, incomplete responses and split replies; resume presence being
literal only, including `No SQL experience` counting as present; the module
importing nothing; registration in both loaders; and the credential never
being reachable from the page.

**Not tested.** No live API call was made, so extraction precision and recall
are unmeasured. Passing these tests measures the code around the model, not
the model's judgement. Whether a returned phrase is genuinely a skill, whether
any skill was missed, and whether required/preferred status was read correctly
are all model decisions that a quotation check cannot verify: a quotation can
be exact and still irrelevant.

To measure extraction quality you need labelled postings — terms, categories,
evidence spans and requirement status marked by a person — with a held-out
set, and precision, recall and F1 reported separately for hard and soft
skills. Include `C`/`C++`/`C#`, `R`, `Go`, Excel used as a verb, negations,
acronyms, combined phrases and employer boilerplate.
